TESTE DE MUITOS USUARIOS SIMULTANEOS - K6

Objetivo
--------
Testar como o backend do My GManager se comporta quando varios usuarios acessam ao mesmo tempo.

Esse tipo de teste ajuda a descobrir:
- tempo medio de resposta;
- p95 e p99 de latencia;
- taxa de erro;
- gargalos no banco;
- limites de Vercel/Neon;
- problemas com autenticacao;
- problemas com rate limit;
- quantidade aproximada de usuarios simultaneos suportada.


1. Ferramenta escolhida
-----------------------
Usar k6.

Motivos:
- scripts em JavaScript;
- bom para testar APIs;
- suporta usuarios virtuais;
- mostra metricas importantes;
- permite thresholds;
- facil de versionar no projeto.

Alternativa:
- Artillery tambem e boa, mas k6 e mais claro para fluxos autenticados.

Documentacao:
- https://grafana.com/docs/k6/latest/
- https://grafana.com/docs/k6/latest/using-k6/metrics/reference/
- https://grafana.com/docs/k6/latest/using-k6/thresholds/

6. Teste simples de rota publica
--------------------------------
Criar:

tests/load/public-smoke.js

Conteudo:

import http from "k6/http"
import { check, sleep } from "k6"

export const options = {
    stages: [
        { duration: "30s", target: 10 },
        { duration: "1m", target: 30 },
        { duration: "30s", target: 0 },
    ],
    thresholds: {
        http_req_failed: ["rate<0.01"],
        http_req_duration: ["p(95)<800"],
    },
}

export default function () {
    const apiUrl = __ENV.API_URL || "http://localhost:3000"

    const res = http.get(`${apiUrl}/`)

    check(res, {
        "status 200": (r) => r.status === 200,
    })

    sleep(1)
}

Rodar:

$env:API_URL="http://localhost:3000"
k6 run tests/load/public-smoke.js


7. Teste com login + leitura de dashboard
-----------------------------------------
Criar:

tests/load/dashboard-read.js

Conteudo:

import http from "k6/http"
import { check, sleep } from "k6"
import { SharedArray } from "k6/data"

const users = new SharedArray("users", function () {
    return JSON.parse(open("./users.json"))
})

export const options = {
    stages: [
        { duration: "30s", target: 5 },
        { duration: "1m", target: 20 },
        { duration: "1m", target: 50 },
        { duration: "30s", target: 0 },
    ],
    thresholds: {
        http_req_failed: ["rate<0.02"],
        http_req_duration: ["p(95)<1000", "p(99)<2000"],
    },
}

export default function () {
    const apiUrl = __ENV.API_URL || "http://localhost:3000"
    const user = users[__VU % users.length]

    const loginRes = http.post(
        `${apiUrl}/auth/login`,
        JSON.stringify({
            email: user.email,
            senha: user.senha,
        }),
        {
            headers: {
                "Content-Type": "application/json",
            },
        }
    )

    check(loginRes, {
        "login 200": (r) => r.status === 200,
        "recebe token": (r) => Boolean(r.json("token")),
    })

    const token = loginRes.json("token")

    if (!token) {
        sleep(1)
        return
    }

    const params = {
        headers: {
            Authorization: `Bearer ${token}`,
        },
    }

    const meRes = http.get(`${apiUrl}/auth/me`, params)

    check(meRes, {
        "me 200": (r) => r.status === 200,
    })

    const tarefasRes = http.get(
        `${apiUrl}/tarefas?inicio=2026-05-01&fim=2026-05-31`,
        params
    )

    check(tarefasRes, {
        "tarefas 200": (r) => r.status === 200,
    })

    sleep(1)
}

Rodar:

$env:API_URL="http://localhost:3000"
k6 run tests/load/dashboard-read.js


8. Cuidado com rate limit
-------------------------
O teste dashboard-read faz login varias vezes.

Isso pode bater no loginLimiter.

Se acontecer muito 429:
- reduzir numero de VUs;
- reduzir duracao;
- criar mais usuarios de teste;
- fazer teste separado para login;
- testar mais rotas autenticadas sem ficar logando toda hora.

Nao desativar rate limit em producao.

Se for necessario facilitar testes em ambiente dev, fazer isso com cuidado e somente com NODE_ENV=development.


9. Metricas importantes
-----------------------
Observar no resultado do k6:

http_req_failed:
- taxa de falha.
- ideal inicial: menor que 1% ou 2%.

http_req_duration:
- tempo de resposta.
- olhar principalmente p95 e p99.

checks:
- se as validacoes passaram.

vus:
- usuarios virtuais ativos.

http_reqs:
- total de requisicoes feitas.

Erros comuns:
- 401: problema com token/auth.
- 429: rate limit.
- 500: erro interno.
- timeout: backend, banco ou rede lentos.


10. Metas iniciais
------------------
Para ambiente local/dev:

p95 abaixo de 800ms: bom
p95 entre 800ms e 1500ms: aceitavel para investigar
p95 acima de 1500ms: precisa olhar gargalo
http_req_failed abaixo de 1%: bom

Para producao em plano free:

p95 abaixo de 1500ms: aceitavel no inicio
p95 acima de 2000ms: investigar
muitos 500: problema serio
muitos 429: rate limit ou teste agressivo demais


11. Teste progressivo recomendado
---------------------------------
Rodar nesta ordem:

1. public-smoke com 10 VUs.

13. API unica: isso e problema?
-------------------------------
Nao.

Ter uma unica API e normal no inicio.

Hoje o My GManager tem:
- um frontend;
- uma API backend;
- um banco.

Isso e suficiente para um projeto pequeno/medio no inicio.

Nao precisa criar varias APIs agora.

Criar mais APIs so faz sentido quando:
- o sistema fica muito grande;
- equipes diferentes cuidam de partes diferentes;
- algum modulo precisa escalar separado;
- ha dominios muito independentes, como pagamentos, notificacoes, IA, etc.

Separar cedo demais aumenta complexidade.

Melhor agora:
- organizar bem controllers/services/repositories;
- melhorar queries;
- usar banco dev;
- testar carga;
- monitorar gargalos.


14. O que e load balancer?
--------------------------
Load balancer e um componente que fica na frente de varias instancias da API.

Ele recebe requisicoes e distribui entre servidores.

Exemplo:

Usuario 1 -> Load Balancer -> API instancia 1
Usuario 2 -> Load Balancer -> API instancia 2
Usuario 3 -> Load Balancer -> API instancia 1

Objetivos:
- dividir carga;
- aumentar disponibilidade;
- permitir escalar horizontalmente;
- tirar uma instancia do ar sem derrubar todo o sistema;
- fazer health checks.


15. Quando usar load balancer?
------------------------------
Usar quando uma unica instancia da API nao for suficiente.

Sinais:
- CPU/memoria do backend sempre alta;
- muitos timeouts;
- muitas requisicoes simultaneas;
- uma instancia cai e derruba tudo;
- usuarios reais crescendo;
- necessidade de alta disponibilidade.

No estado atual do projeto, provavelmente ainda nao precisa.


16. Como fazer load balancer no futuro?
---------------------------------------
Opcoes:

1. Plataforma gerenciada
- Railway, Render, Fly.io ou similares podem escalar instancias.
- A plataforma geralmente faz o balanceamento.

2. AWS
- Rodar backend em ECS/Fargate, EC2 ou Elastic Beanstalk.
- Usar Application Load Balancer.
- Banco separado, por exemplo Neon ou RDS.

3. Kubernetes
- Mais avancado.
- Usar Service/Ingress.
- Nao recomendado agora para este projeto.

4. Nginx
- Pode ficar na frente de varias instancias Node.
- Bom para aprender, mas aumenta manutencao.


17. Cuidado com sessoes
-----------------------
Para escalar a API com load balancer, a API deve ser stateless.

No My GManager isso ja esta bem encaminhado:
- access token JWT no frontend;
- refresh token em cookie;
- refresh tokens no banco.

Evitar guardar estado de sessao em memoria local do servidor.

Se uma instancia depende de memoria local, o load balancer pode mandar a proxima requisicao para outra instancia e quebrar o fluxo.
